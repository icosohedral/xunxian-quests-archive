# 寻仙任务数据库项目决策记录

> 状态日期：2026-07-26  
> 记录目的：说明开发过程中发现了什么问题、为什么修改，以及最终怎样处理。  
> 当前网站版本：`v1.0.0`

本文不是数据表的完整抄录。称号、状态、阵营、地区等大表仍以原始资源为准；本文记录
的是影响数据库和网站行为的分析过程与决定，方便后续维护者理解“为什么这样做”。

## 1. 原始文本编码统一

### 发现的问题

`original_data` 中部分包含中文的文本出现乱码。资源并非全部使用同一编码，读取时若
把 GBK 文本当成 UTF-8，或把已经是 UTF-8 的文本重复转换，都会破坏内容。

### 为什么修改

任务名称、对话、NPC 名称和对象名称是后续关联的基础。编码不稳定会造成同一名称无法
匹配，也会让数据库永久保存乱码。

### 最终处理

- 逐文件判断可读编码，只转换确认存在问题的文件；
- 统一输出为 UTF-8；
- 转换过程写入 `encoding_conversion_manifest.json`；
- 转换前完整备份为 `original_data_before_utf8_20260724.tar.gz`；
- 后续建库只读 `original_data`，不在流水线中反复转换。

## 2. 以 `quest_info` 为任务主表

### 发现的问题

任务资源分散在多个文件中，单独读取 `quest_info.txt` 只能得到任务骨架；任务文本、
追踪目标、NPC、分类、奖励和关系需要从其他文件补齐。

### 为什么修改

若把每个文件当成独立列表，无法回答“一个任务有哪些完整信息”，也无法从角色或前置
任务跳转到相关任务。

### 最终处理

- 以 `original_data/mb/quest/quest_info.txt` 为任务主表；
- 参考 `original_data/index_list.txt` 定位其他资源；
- 通过任务 ID、对象类型 ID、对象 ID、目标 ID 等建立关联；
- 所有关联结果保留来源文件、原始行号、原始值和运行 ID；
- 无法确认的引用保留为未解析记录，不伪造关联。

## 3. `quest_info` 64 个字段的解释策略

### 发现的问题

`quest_info` 没有足够完整的官方字段说明。部分列可以通过取值分布和关联文件确定，
部分列只能推测，贸然正式命名会把推测固化为错误事实。

### 为什么修改

数据库需要可查询字段，但也必须允许未来推翻早期判断。

### 最终处理

- 高置信字段使用正式语义名称；
- 中置信字段使用经 G01 审批的临时名称；
- 低置信字段继续以 `col_###` 和原值保存；
- 字段字典记录置信度和证据；
- G01 批准了临时命名、保守保存和任务 `11257` 的版本策略。

## 4. 任务 ID `11257` 的多版本处理

### 发现的问题

资源中存在两个相同任务 ID `11257`，但内容并不完全相同。强行覆盖会丢失其中一个
版本，作为两个普通搜索结果又会让用户误以为是两个独立任务。

### 为什么修改

需要同时满足原始数据无损和前台易读。

### 最终处理

- SQLite 底层保存两个版本并标记版本号；
- `quest_identity` 中只保留一个任务身份；
- 网站合并成一个任务入口，安全字段统一展示；
- 冲突内容和别名仍保存在详情模型中；
- 该策略经 G01 审批。

## 5. 任务文本标签显示

### 发现的问题

任务对话中存在 `<enemy>`、`<target>`、`<character>`、`<c>`、`<area>` 等游戏内部
标签。直接显示会影响阅读；全部删除又会丢失角色和目标关系。

### 为什么修改

标签既包含排版控制，也包含对象引用，必须按语义分别处理。

### 最终处理

- `<enemy>`、`<target>`、`<character>` 和可唯一匹配的 `<friend>` 建立对象链接；
- `<name>` 显示为“玩家”；
- `<c>` 只控制颜色，因此去掉标签并保留内部文字；
- `<area>`、`<brief>`、`<aim>` 去掉标签并保留文字；
- 无法匹配对象的 `<enemy>` 去标签保留名称；
- 包含“提示：”的导航说明按普通提示文字展示；
- 常见 `target` 拼写错误和全角冒号先规范化再解析；
- `item` 标签根据实际内容作为提示语义处理，不一律当作任务道具；
- `<ic:ID>` 尚无可靠资源对应关系，暂不生成链接。

## 6. 动态玩家称谓

### 发现的问题

`<character:ID>` 有时不是固定 NPC，而是系统根据玩家条件选择的称谓。最初无法从普通
NPC 表找到对应名称。

### 为什么修改

把它显示为“未解析角色”会误导用户；直接固定为一个称谓又会丢失其他候选。

### 最终处理

- 识别角色称谓模板及其候选值；
- 页面默认显示第一个称谓；
- 保留链接，用户可查看和切换其他候选；
- 对象详情不显示“称谓模板 ID”和“候选数量”等内部字段。

## 7. 称号 ID 映射

### 发现的问题

任务“【天劫路】十方幻化心空明”的奖励显示“称号ID 505”，前置需求显示
“称号ID 506”。这说明对象类型已识别为称号，但网站没有接入称号名称表。

### 为什么修改

裸 ID 对普通访客没有意义，而且前置条件需要明确表达为“需要某个称号”。

### 最终处理

- 确认对象类型 `21` 表示称号；
- 找到权威资源 `original_data/mb/etc/title_list.txt`；
- 按第 2 列称号 ID 映射第 1 列称号名称；
- 同时预留对象类型 `22` 的 `title_group.txt` 称号组映射；
- 扫描所有任务中的称号条件与奖励，而不是只修示例任务；
- 任务引用的称号 ID 均已匹配；
- ID `505` 显示“十方名士”，ID `506` 显示“十方上师”；
- 条件显示“称号 十方上师”，奖励类型显示“称号”。

## 8. 角色状态 ID 映射

### 发现的问题

任务“【副本】大战如意妖仙”的奖励和前置条件只显示“状态 ID 21056”等裸 ID。

### 为什么修改

状态是任务条件的一部分，缺少名称会让条件和奖励不可理解；只修一个 ID 也会留下同类
遗漏。

### 最终处理

- 确认对象类型 `20` 表示状态；
- 找到权威资源 `original_data/mb/skill/state_group.txt`；
- 按第 2 列状态 ID 映射第 1 列状态名称；
- 全量扫描任务条件和奖励中的状态引用；
- 67 个被任务引用的不同状态 ID 均已匹配，覆盖 211 个任务、234 处引用；
- 页面显示“状态 + 名称”，不再显示裸状态 ID。

## 9. 阵营声望映射和显示

### 发现的问题

任务“【正传】阅秘书解析天劫”的阵营声望显示为 ID `15`，说明任务侧阵营表不完整，
但游戏的通用阵营资源中存在名称。

### 为什么修改

阵营奖励必须说明属于哪个阵营；同时原页面使用乘号显示声望数值，语义也不正确。

### 最终处理

- 同时检查 `mb/quest/quest_camp.txt` 和通用表 `mb/camp/camp.txt`；
- 用通用阵营表补足任务侧缺失名称；
- ID `15` 匹配为“鬼谷仙派”；
- 扫描并修复其他同类遗漏；
- 前台字段名改为“阵营声望”；
- 数值显示为 `+xxx`，不使用 `×xxx`。

## 10. 经验值奖励

### 发现的问题

结构化奖励表中没有完整显示经验值，但 `quest_info` 原始列里存在 `cp*数值` 或
`exp*数值` 形式的经验公式。

### 为什么修改

经验是任务奖励的主要组成部分，忽略会让奖励信息明显不完整。

### 最终处理

- 从对应原始字段识别 `cp*数字` 和 `exp*数字`；
- 生成“经验值”展示奖励，不改写原始任务记录；
- 数值一万以上用整数“万”，一亿以上用整数“亿”；
- 经验值和阵营声望都用加号表示获得。

## 11. 主类型与子类型

### 发现的问题

原始分类中既有“副本任务”这样的总类，也有“玉灵山”“五行通天阵”等具体分类；
地区重复任务还会产生大量平级标签。全部平铺会让筛选栏冗长并出现语义重复。

### 为什么修改

用户先判断任务性质，再选择具体副本、活动或地区，比在一长串标签中查找更清晰。

### 最终处理

- 网站查询层生成“主类型 + 子类型”，不改写数据库原分类；
- 名称以“支线”结尾的归入“支线任务”，地区名作为子类型；
- 名称以“重复”结尾的归入“重复任务”，地区名作为子类型；
- 天劫路、水月镜花等归入“系列任务”；
- 玉灵山、五行通天阵、灵谷、闯三关、鬼王乱世归入“副本任务”；
- 官府当差、仙派当值、水下两派、仙友会、降妖擂台归入“声望任务”；
- 门派、跨阵营、联盟、跨区、怒海争霸、元宝堂归入“阵营任务”；
- 联动、定时、周年庆、极限挑战、对抗战场、砺炼、休闲归入“活动任务”；
- 奇缘任务归入“重复任务”；
- 有剩余任务时生成“未分类”，但若只有这一个子类型则不显示；
- 详情中的子类型为“未分类”时只显示主类型；
- 主类型在筛选栏按任务数量降序排列。

## 12. 地区与子地区

### 发现的问题

原始地区粒度不一致。桃花林、青牛坡、京城南郊等小区域与小桑村、宁海县、京城等
大区并列，会让地区筛选过长；但详情若只显示大区，又会丢失任务实际地点。

### 为什么修改

筛选需要简洁，任务详情需要准确，两者不应强行使用同一显示粒度。

### 最终处理

- 结合 `quest_target.txt`、`scn/prov_info.txt` 和数据库 `area` 表确认地区层级；
- 筛选栏只显示大区，并把人工确认的子地区纳入大区查询；
- 详情保留原所属地区，以“大区·子地区”显示；
- 例如筛选“小桑村”，详情可显示“小桑村·桃花林”；
- 已人工归并宁海县—青牛坡、京城—京城南郊等关系；
- 多种独立副本地点统一归入“副本场景”筛选；
- 地区筛选按该地区最低任务等级从低到高排列；
- 筛选选项不显示“xx级起”。

任务“【正传】阅秘书解析天劫”原先地区异常。核对任务语境后将其原所属地区修正为
“云梦山”；筛选时按归并规则进入“东山岛”，详情仍显示“云梦山”。

## 13. 页面中的内部信息取舍

### 发现的问题

早期原型展示任务 ID、地区 ID、对象 ID、来源文件、原始行号和原始标签等解析证据。
这些信息便于开发排错，但会干扰普通用户阅读。

### 为什么修改

网站定位已经从内部验证工具转为公开任务存档，界面应优先呈现游戏资料而非数据库细节。

### 最终处理

- 搜索栏不提供任务 ID 搜索；
- 列表不显示任务 ID、接取人和“有文本”；
- 对象详情不显示对象 ID、原始来源、原始行号和“已解析”状态；
- 移除所有“查看原始标签文本”选项；
- 保留这些数据在 SQLite 和 API 中用于追溯，不从底层删除；
- 原“原始来源”位置改为“相关任务”；
- 点击角色或目标后展示其参与的其他任务。

## 14. 检索和相关任务分页

### 发现的问题

检索结果过多，整页翻页会导致任务详情和页面状态一起刷新，速度和连续阅读体验都较差。
从任务关系跳转时还会丢失左侧检索上下文。

### 为什么修改

任务研究通常需要在同一批搜索结果中连续打开多个任务，检索上下文应保持稳定。

### 最终处理

- 检索结果每页最多 5 条并显示总页数；
- 排序改为任务等级从低到高，同级按任务 ID 稳定排序；
- 左侧翻页改为局部刷新；
- 预取相邻页，降低连续翻页等待；
- 从任务语境、前置任务或相关任务跳转时保留搜索条件和页码；
- 相关任务独立分页，每页最多 5 条。

## 15. 今日来访统计

### 发现的问题

早期统计随页面请求增长，刷新、爬虫和重复访问都可能计数，因此数字增加过快。

### 为什么修改

“今日来访”应该更接近当天独立浏览器数量，而不是 HTTP 请求次数。

### 最终处理

- 浏览器首次访问生成匿名随机 ID 并保存到 `localStorage`；
- JavaScript 调用 `/api/visit`；
- D1 按“日期 + 匿名 ID”去重；
- 同一浏览器同一天只计一次；
- 不执行 JavaScript 的爬虫和 `curl` 不计数；
- 不采集账号、IP 或个人身份信息；
- 历史统计继续保留，但旧数字不视为严格独立访客数。

## 16. Cloudflare 部署架构

### 发现的问题

本地原型依赖 SQLite 文件和完整资源目录，不能直接作为 Cloudflare Worker 部署。

### 为什么修改

目标域名已托管在 Cloudflare，需要适配 Worker、D1 和静态资源的运行方式。

### 最终处理

- 本地版本继续使用 FastAPI + 只读 SQLite；
- 线上版本使用 Cloudflare Python Worker + FastAPI；
- 任务查询数据转换为 D1；
- 访问统计使用独立 D1；
- CSS、JavaScript 和图标使用 Workers Static Assets；
- 构建脚本从本地模板、样式和分类规则生成线上模块；
- 自定义域名使用 `quests.xunxian.wiki`。

## 17. 网站版本号与发布规则

### 需求

左上角标题需要显示网站版本。当前版本从 `v1.0.0` 开始，后续每次正式同步
Cloudflare 时，小版本号加一。

### 最终处理

- 左上角“寻仙任务存档”旁以辅助字号显示 `v1.0.0`；
- 版本唯一来源为 `apps/quest_viewer/VERSION`；
- 本地 FastAPI 和线上 Worker 都读取同一版本来源；
- Cloudflare 构建生成 `src/generated_version.py`；
- 后续正式同步统一执行：

```bash
cd apps/quest_viewer_cloudflare
uv run python scripts/deploy_release.py
```

- 发布脚本按 `1.0.0 → 1.0.1 → 1.0.2` 递增补丁版本；
- 脚本先更新版本、同步模板与静态资源，再部署；
- 部署失败时自动回滚版本号和生成文件；
- 不再把裸 `pywrangler deploy` 作为日常发布命令。
